# PostgreSQL, векторный поиск и ИИ-библиотекарь — экспериментальная реализация

## Что реализовано

- PostgreSQL 16 с расширениями `vector` (pgvector) и `pg_trgm` хранит **вторичный поисковый индекс**; SQLite остаётся основной базой каталога, пользователей и журнала. Полный переход основной базы на PostgreSQL не выполнен.
- Индексатор создаёт многоязычные embeddings локальной моделью `intfloat/multilingual-e5-small` (384 измерения; зафиксирована ревизия модели). Для поиска используется комбинация PostgreSQL FTS (`simple`), trigram по названию и косинусной близости pgvector; результаты объединяются RRF. Для нескольких предметов есть небольшой явный словарь синонимов RU/KZ/EN — это не полноценный переводчик.
- Векторный поиск по умолчанию отбрасывает совпадения с cosine similarity ниже 0,80. Это экспериментальный порог, **не гарантия релевантности**; задаётся `QOR_MIN_SIMILARITY`. При фильтрах используется точный векторный проход, чтобы приблизительный индекс не терял записи из малых выборок.
- Поисковые результаты сверяются с текущими карточками SQLite и их хешами: изменённые или удалённые карточки пропускаются до переиндексации. Источником библиографических данных остаётся SQLite. На экране показано число проиндексированных записей, но счётчик может включать устаревшие записи: он не доказывает актуальность каждой карточки.
- ИИ-библиотекарь получает найденные метаданные и предлагает идентификаторы до пяти записей. Модель может выбирать только из первых шести переданных ей записей; сервер проверяет ID и повторно проверяет актуальность карточек. Произвольный текст модели пользователю не показывается — название, автор, год и ссылки берутся из SQLite. Это ограниченный подбор литературы, не свободный многоходовый чат и не анализ полных текстов. Даже при достоверных ID релевантность и качество исходных метаданных не гарантированы.
- Поддерживаются экспериментальная локальная LLM `Qwen/Qwen2.5-0.5B-Instruct` (зафиксированная ревизия) или совместимый HTTPS Chat Completions API с JSON-ответом. Локальная модель может ошибаться, плохо следовать формату и медленно отвечать на CPU.

## Развёртывание для локальной проверки

Не используйте эту схему в публичной сети. Для тестирования нужны Python 3.12+, достаточная память и место для загрузки моделей, PostgreSQL с установленными расширениями pgvector и pg_trgm. Первое использование моделей загружает их с Hugging Face; версии фиксированы в коде. Установите зависимости:

```bash
python -m venv .venv
source .venv/bin/activate
# Для CPU отдельно установите совместимую с вашей платформой сборку PyTorch.
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements-ai.txt
```

Например, при наличии Docker можно поднять *только тестовый* PostgreSQL из `compose.search.yaml`:

```bash
export QOR_POSTGRES_PASSWORD='придумайте_длинный_тестовый_пароль'
docker compose -f compose.search.yaml up -d
export QOR_PG_DSN='postgresql://qor:ВАШ_URL_КОДИРОВАННЫЙ_ПАРОЛЬ@127.0.0.1:5432/qor_search'
export QOR_DB_PATH='./data/qor.db'
export QOR_LLM_BACKEND='local'
```

В DSN пароль со спецсимволами необходимо URL-кодировать. Пароли и ключи не добавляйте в код и репозиторий. `.env.example` — справочный пример, приложение **не загружает `.env` автоматически**. Docker Compose в этой среде не тестировался; PostgreSQL и расширения были собраны и протестированы локально из исходников.

Инициализируйте каталог QOR, импортируйте подтверждённые записи КАБИС по `KABIS_IMPORT.md`, остановите другие процессы записи и сделайте резервную копию SQLite. Затем постройте индекс:

```bash
python -m app.index_catalog --batch-size 16
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Для быстрой проверки можно передать `--limit 240`, но это даст заведомо **неполный** индекс. Первое полное индексирование 37 тысяч записей на CPU может занять длительное время. Индекс сохраняется по партиям; повторная команда переиндексирует изменённые записи и продолжит работу. Скопированная SQLite-база сохраняет свой ID каталога, поэтому не используйте одновременно расходящиеся копии с одним PostgreSQL-индексом: для разных независимых каталогов требуется отдельный идентификатор или отдельная база индекса.

После добавления/редактирования/импорта записей повторно запускайте индексатор: автоматической фоновой синхронизации пока нет. Удалённые источники отбрасываются при поиске, но устаревшие векторы автоматически из таблицы не удаляются. Сохраняйте резервные копии SQLite и PostgreSQL по отдельности; поисковый индекс можно перестроить из SQLite, но резервное копирование и восстановление PostgreSQL в рамках пилота ещё не испытаны.

В разделе поиска выберите «Гибридный PostgreSQL»; раздел «ИИ-библиотекарь» использует только гибридный поиск. Если PostgreSQL, индекс или модель недоступны, API вернёт 503, а не заявит, что семантический поиск работает. Обычный поиск SQLite доступен отдельно.

## Внешний LLM API (необязательно)

```bash
export QOR_LLM_BACKEND=api
export QOR_LLM_BASE_URL='https://адрес-провайдера/v1'
export QOR_LLM_MODEL='имя-модели'
# Установите QOR_LLM_API_KEY безопасным способом в окружении сервера.
```

Провайдер должен поддерживать endpoint `/chat/completions` и формат `response_format: json_object`. Запрос пользователя и метаданные до шести материалов отправляются провайдеру. Используйте это только при наличии разрешения на передачу данных и подходящих условий обработки. В этом окружении реальный внешний API не тестировался; локальная модель тестировалась.

## API

- `POST /api/search/hybrid` принимает те же поля, что и обычный поиск: `query`, `language`, `material_language`, `kind`, `year`, `limit`. `count` означает число **показанных кандидатов**, а не общее число релевантных записей. `indexed`, `catalog_total`, `stale_candidates_skipped`, `query_expansion` помогают оценить состояние индекса.
- `POST /api/assistant` принимает `{"question":"...","language":"ru"}` или `kk`, возвращает безопасный шаблонный ответ и список проверенных `sources` со ссылками на `/item.html?id=...`.
- `GET /api/health` сообщает, настроены ли компоненты, но не проверяет доступность PostgreSQL или модели.

## Проверка и ограничения

- Интеграция проверена на PostgreSQL 16.11 + pgvector 0.8.0, embeddings E5 и фактической локальной LLM Qwen. Выполнены запросы по выборке из 240 записей реального каталога; отдельно построен частичный индекс 1 000 из 37 703 записей за 68,59 секунды. Весь фонд не индексировался. У 133 ранее отклонённых записей заглавие не определялось — они не индексировались.
- На тестовых примерах поиск находил литературу по горному делу на русском и казахском, включая результаты на другом языке. При этом модель возвращала и нерелевантные материалы; квалифицированная проверка и размеченный набор запросов ещё необходимы.
- В одиночном тесте локальный ИИ на CPU отвечал примерно 24–36 секунд. Первый запрос также включает загрузку моделей. Это не нагрузочный тест.
- Сборка не готова к пилоту: нет полной миграции на PostgreSQL, автоматической синхронизации индекса, полноценного диалога, всех языков интерфейса, SSO, распределённого ограничения частоты запросов, независимого аудита безопасности и испытаний на полном индексе. Публичный ИИ-эндпоинт потребляет много ресурсов; нужна защита от перегрузки. Docker/Render, производственная инфраструктура и реальные внешние LLM-провайдеры не проверялись.

Обычный `Dockerfile` содержит только зависимости базового MVP и не подходит для режима ИИ. `Dockerfile.ai` — отдельный экспериментальный CPU-образ с зависимостями моделей; он также не собирался и не тестировался в этой среде. Для него нужны подключаемые постоянные хранилища SQLite и кэша моделей, а также сетевой доступ к PostgreSQL.
